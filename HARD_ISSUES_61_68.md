## Issue 61: [Core Scanner] Build a Symbolic Execution Engine for Path-Aware Vulnerability Detection

**Priority:** 🔴 Critical
**Area:** Core Scanner / Advanced Static Analysis
**Files:** `src/scanners.rs`, `src/analysis.rs`, `src/security_analyzer.rs`, `src/differential_fuzzing/execution_tracer.rs`

### Description

The current security scanner (`src/scanners.rs`, `src/security_analyzer.rs`) relies on regex-based pattern matching and shallow AST traversal to detect vulnerabilities. While effective for surface-level issues (missing `require_auth`, unchecked arithmetic), this approach cannot detect vulnerabilities that manifest only along specific execution paths involving multiple branches, loops, and state-dependent conditions. For example, a reentrancy bug that only triggers when `amount > balance / 2` AND `sender == fee_recipient` AND `block.timestamp % 1000 == 0` will never be found by pattern matching — it requires path-sensitive analysis.

A **symbolic execution engine** would represent contract state and function inputs as symbolic variables rather than concrete values, then explore all feasible execution paths by solving path constraints with an SMT solver. At each path endpoint, the engine checks vulnerability conditions: "Is there any path where `balance[user]` can go negative?" or "Is there any path where the checks-effects-interactions pattern is violated?" This is the same technique used by tools like Mythril, Manticore, and KEVM for Ethereum — adapted for Soroban's WASM-based execution model and Stellar's account/trustline architecture.

The core challenge is multi-layered: (1) lifting Soroban WASM bytecode to an intermediate representation suitable for symbolic execution, (2) modeling Stellar-specific operations (trustline changes, account merges, sequence number bumps) as symbolic constraints, (3) implementing a constraint solver that can handle 128-bit integer arithmetic (i128 is native to Soroban), (4) managing path explosion through heuristic search strategies and loop bounding, and (5) integrating the symbolic engine with the existing concrete fuzzer to form a concolic (concrete + symbolic) execution loop where concrete runs guide symbolic exploration.

### Acceptance Criteria

- [ ] **Phase 1 — IR Lifting:** Implement a WASM-to-IR lifter that translates Soroban contract WASM into a three-address-code intermediate representation with explicit control flow graphs (CFG). Each IR instruction must preserve enough metadata to reconstruct source-level vulnerability locations. Support the full Soroban WASM instruction set including `call_indirect`, `memory.grow`, and host function imports.
- [ ] **Phase 2 — Symbolic State Model:** Define a `SymbolicState` struct containing: symbolic representations of the Soroban ledger (account balances, trustlines, contract data entries), a symbolic call stack with per-frame local variables, and a path constraint set (`Vec<SmtConstraint>`). Every read from contract storage produces a fresh symbolic variable; every write updates the symbolic state map.
- [ ] **Phase 3 — Stellar Semantics:** Model Stellar-specific operations as symbolic constraints: `require_auth` becomes a constraint that the caller address matches an authorized set, trustline `authorize`/`deauthorize` constrains the trustline flags, account merge constrains the destination account's `num_subentries`, sequence number increments are modeled as strictly monotonic. The model must capture at least 15 Stellar-specific operations.
- [ ] **Phase 4 — Constraint Solver Integration:** Integrate with `z3` (via the `z3` Rust crate or FFI) for SMT solving. Define theories for bit-vectors (BV) of width 128 (for i128), arrays (for storage maps), and uninterpreted functions (for host function calls whose semantics are unknown). Implement incremental solving: push/pop constraints as the engine explores paths so the solver state is reused across sibling paths.
- [ ] **Phase 5 — Vulnerability Checkers as Path Conditions:** Refactor existing vulnerability detectors (reentrancy, integer overflow, access control, invariant violation) into path-condition checkers. Each checker defines a `check(state: &SymbolicState, path: &PathConstraint) -> Option<VulnerabilityReport>`. The engine calls all checkers at each path endpoint and also at points where a checker registers interest (e.g., after every external call for the reentrancy checker).
- [ ] **Phase 6 — Path Exploration Strategy:** Implement a search strategy selector: BFS (complete but memory-intensive), DFS (fast but can get stuck), and a coverage-guided best-first search using a heuristic that prioritizes paths approaching unvisited CFG edges. Add a configurable `max_depth` (default 1000 instructions) and `max_paths` (default 10,000) to bound exploration. Support loop summarization: when a loop body is side-effect-free except for a counter, replace it with a closed-form summary rather than unrolling.
- [ ] **Phase 7 — Concolic Mode:** Implement a hybrid mode where concrete fuzzer inputs (`src/analysis_guard/fuzz.rs`) are executed concretely, the execution trace is recorded, and then one branch point is flipped symbolically to explore a neighboring path. This combines the speed of concrete execution with the coverage of symbolic exploration. The concolic loop runs until either `max_iterations` is reached or no new coverage is found after `stagnation_limit` iterations.
- [ ] **Phase 8 — Benchmark Suite:** Create a benchmark suite of 20 Soroban contracts with known vulnerabilities that are undetectable by the current pattern-matching scanner but findable by symbolic execution. Include: multi-condition reentrancy, path-dependent integer overflow, state-dependent access control bypass, and loop-dependent invariant violation. Measure and report: time-to-first-finding, total paths explored, false positive rate, and comparison against the current scanner.
- [ ] **Phase 9 — CLI Integration:** Add `stellar-scanner scan --symbolic [--max-depth N] [--max-paths M] [--timeout T]` that runs the symbolic engine as a complement to the existing concrete scanner. Results from both are merged: findings unique to symbolic execution are tagged `detection_method: symbolic` in the report.
- [ ] **Documentation:** Write `docs/SYMBOLIC_EXECUTION.md` covering: the IR format, SMT encoding of Stellar operations, path search heuristics, known limitations (loop unrolling bounds, unmodeled host functions), and guidance on when to use symbolic vs. concrete scanning.

## Issue 62: [Analysis] Cross-Contract Taint Tracking and Composability Attack Surface Analysis

**Priority:** 🔴 Critical
**Area:** Core Scanner / Inter-Procedural Analysis
**Files:** `src/differential_fuzzing/cross_contract_simulator.rs`, `src/scanners.rs`, `src/analysis.rs`

### Description

The `CrossContractSimulator` in `src/differential_fuzzing/cross_contract_simulator.rs` simulates cross-contract calls at a single level of depth (`A → B`), and Issue #27 addresses extending this to recursive call chains. However, neither addresses **taint tracking** — the analysis of how attacker-controlled data flows through a network of contracts and reaches sensitive operations. In DeFi protocols on Soroban, a typical architecture involves 5–15 contracts: a router, several pool contracts, a factory, a fee distributor, an oracle, and a governance token. A vulnerability in one contract can be exploited by crafting a call sequence that starts from a completely different entry point, passes through multiple intermediate contracts, and finally triggers the vulnerable code path with attacker-controlled parameters.

This issue requires building a **cross-contract taint analysis engine** that: (1) constructs a call graph from a set of deployed contract WASM binaries, (2) identifies "source" points where external (attacker-controlled) data enters the contract system (function parameters of `pub` functions, oracle responses, cross-contract call return values), (3) identifies "sink" points where sensitive operations occur (balance transfers, `require_auth` checks, storage writes to privileged keys, token mints), (4) propagates taint through the call graph using a flow-sensitive, context-sensitive analysis, and (5) reports paths where tainted data reaches a sink without proper sanitization or authorization checks.

The complexity comes from: handling indirect calls via `call_indirect` (dynamic dispatch), tracking taint through storage (if a value is stored tainted and later loaded, it remains tainted), modeling host function semantics (what does `stellar.transfer` do to taint?), and scaling the analysis to 50+ contract systems without exponential blowup in the call graph.

### Acceptance Criteria

- [ ] **Phase 1 — Call Graph Construction:** Build a `CrossContractCallGraph` from a set of WASM modules. For each module, extract: (a) exported function signatures, (b) cross-contract call sites (`call_indirect` instructions with known host function targets), (c) import declarations showing which external contracts are called. Represent the graph as `HashMap<(ContractId, FunctionName), Vec<(ContractId, FunctionName, ArgumentMapping)>>` where `ArgumentMapping` describes how caller arguments map to callee parameters.
- [ ] **Phase 2 — Taint Source Identification:** Define `TaintSource` as any point where data originates outside the contract system: function parameters of externally-callable (`pub`) functions, return values from cross-contract calls, data read from oracle/pricer contracts, and the `env.ledger().timestamp()` and `env.ledger().sequence()` values. Each source is annotated with a `TaintTag { origin: SourceOrigin, constraints: Vec<TaintConstraint> }`.
- [ ] **Phase 3 — Taint Sink Identification:** Define `TaintSink` as any point where sensitive operations occur: `token.transfer()`, `token.mint()`, `token.burn()`, `env.storage().instance().set()`, `require_auth()`, `require_auth_for_args()`, account merge, trustline modification, and admin function calls. Each sink defines a `requires_clean` check: does this sink expect its arguments to be free of taint (e.g., a transfer amount should be validated), or is taint acceptable (e.g., a log event can accept tainted data)?
- [ ] **Phase 4 — Flow-Sensitive Taint Propagation:** Implement a dataflow analysis over each function's control flow graph. Track, at each program point, a `TaintSet` mapping each local variable and stack slot to a set of `TaintTag`s. Propagation rules: (a) assignment copies taint, (b) binary operations merge taint from both operands, (c) `if` conditions do not taint the condition variable (the branch itself is tracked separately), (d) storage `get` after a matching `set` with tainted value returns tainted, (e) cross-contract call arguments become tainted at the callee's parameter sites if the arguments were tainted at the call site.
- [ ] **Phase 5 — Context Sensitivity:** Implement call-site sensitivity with a configurable `k`-limit (default k=2): each function is analyzed separately for each calling context of depth k. Use a `CallString` approach where the context is the sequence of the last k call sites. This prevents false positives from taint that flows into a function but is validated differently in different calling contexts.
- [ ] **Phase 6 — Inter-Contract Taint Flow:** When a cross-contract call is encountered: (a) map the caller's tainted arguments to the callee's parameter taint set, (b) recursively analyze the callee (respecting context-sensitivity depth), (c) map the callee's return value taint back to the caller. Use a `TaintSummary` cache: after analyzing a function in a given context, cache `(inputs_tainted: BitSet, outputs_tainted: BitSet)` to avoid re-analysis.
- [ ] **Phase 7 — Vulnerability Report Generation:** For each path where a tainted value reaches a sink that `requires_clean`, generate a `ComposabilityVulnerability` report containing: the full call chain (entry contract → ... → vulnerable contract), the taint propagation path (source → intermediate variables → sink), the specific constraint under which the path is feasible, and a severity score based on sink sensitivity and taint origin.
- [ ] **Phase 8 — Visualization:** Add a `--taint-graph-output` flag that produces a DOT-format graph showing contracts as subgraphs, taint flows as edges colored by taint origin, sinks highlighted in red, and the shortest taint-to-sink path highlighted. Integrate with the frontend `VulnerabilityReport` component to display taint paths as expandable call chains.
- [ ] **Phase 9 — Benchmark and False Positive Analysis:** Create a benchmark suite of 10 multi-contract DeFi protocol simulations (AMM, lending, staking, bridge, governance). For each, manually annotate known taint flows and verify the analysis finds them. Measure false positive rate against a ground-truth set. Target: recall > 90%, precision > 70%.
- [ ] **Documentation:** Write `docs/CROSS_CONTRACT_TAINT_ANALYSIS.md` covering: the taint propagation rules, context-sensitivity configuration, known limitations (dynamic dispatch approximation, unmodeled host functions), and interpretation of taint flow reports.

## Issue 63: [Economic Security] Build an Economic Exploit Simulation Framework for Flash Loan, Oracle Manipulation, and MEV Detection

**Priority:** 🔴 Critical
**Area:** Core Scanner / Economic Security
**Files:** `src/detectors/time-based-attack-detector.js`, `src/differential_fuzzing.rs`, `src/differential_fuzzing/ledger_snapshot_integration.rs`

### Description

The scanner currently focuses on code-level vulnerabilities (reentrancy, integer overflow, access control) but has no capability to detect **economic exploits** — attacks that do not exploit a code bug but rather manipulate the economic design of a protocol. The most impactful DeFi exploits in recent history have been economic: flash loan attacks on lending protocols, oracle price manipulation draining AMM pools, and MEV sandwich attacks extracting value from user transactions. These attacks are invisible to pattern-matching scanners because the contract code is technically correct — it's the economic assumptions that are violated.

This issue requires building an **economic exploit simulation framework** that models a Soroban DeFi protocol as a system of interacting agents with economic incentives, then searches for sequences of transactions that produce profitable attacks. The framework must: (1) model DeFi primitives (AMM pools with xy=k curves, lending pools with collateralization ratios, oracles with price feeds, staking with reward rates), (2) simulate multi-transaction attack sequences within a single ledger (flash loan: borrow → manipulate → profit → repay), (3) detect oracle manipulation by modeling how price feeds can be moved by large trades, (4) detect MEV opportunities by simulating transaction reordering within a ledger close, and (5) quantify exploit profitability to distinguish theoretical vulnerabilities from practically exploitable ones.

The technical challenge is immense: the search space of possible transaction sequences is combinatorially explosive. The framework must use heuristic-guided search (genetic algorithms, Monte Carlo tree search) to find profitable exploits without exhaustive enumeration. It must also model Soroban-specific economics: Stellar's fixed low fees change MEV calculus compared to Ethereum, Soroban's 3-5 second ledger close time bounds sandwich attack windows, and the lack of a public mempool on Stellar changes front-running dynamics.

### Acceptance Criteria

- [ ] **Phase 1 — Economic Primitive Library:** Build a `DeFiPrimitives` module containing configurable models of: (a) `ConstantProductAMM` — xy=k pool with swap fee, (b) `StableswapPool` — curve-based stablecoin pool, (c) `LendingPool` — over-collateralized lending with liquidation threshold, (d) `TWAPOracle` — time-weighted average price with configurable window, (e) `StakingRewards` — reward rate proportional to stake share, (f) `GovernanceToken` — voting power proportional to balance. Each primitive exposes a `simulate(operation) -> StateChange` interface used by the exploit search engine.
- [ ] **Phase 2 — Attacker Agent Model:** Define `AttackAgent` with capabilities: (a) execute flash loans from any lending pool (borrow any amount, must repay within same transaction), (b) submit any sequence of swap/trade transactions to AMM pools, (c) manipulate oracle prices by executing trades within the TWAP window, (d) reorder transactions within a simulated ledger close (for MEV), (e) deploy temporary contracts to execute complex multi-step attack logic. The agent's objective function is `profit_after_gas = final_balance - initial_balance - gas_costs`.
- [ ] **Phase 3 — Transaction Sequence Search:** Implement three search strategies, selectable by configuration: (a) **Breadth-first beam search** with beam width K=100 — explore transaction sequences up to depth D (default 5), keeping the K most profitable at each level, (b) **Genetic algorithm** — population of transaction sequences, crossover combines two sequences at a cut point, mutation inserts/removes/replaces a transaction, fitness = profit, (c) **Monte Carlo tree search** — treat transaction selection as a game tree, UCB1 for node selection, simulate with random policy, backpropagate profit.
- [ ] **Phase 4 — Oracle Manipulation Detection:** Implement specific detection logic: if a protocol uses a spot price from an AMM pool as an oracle, the framework tests whether an attacker can: (a) execute a large swap to move the spot price beyond a threshold, (b) trigger protocol operations that use the manipulated price (liquidation, minting, borrowing), (c) reverse the manipulation (swap back), and (d) profit from the difference. Report oracle manipulation vulnerabilities with the required capital, price deviation, and profit estimate.
- [ ] **Phase 5 — MEV Sandwich Detection:** Model a ledger close as a sequence of transactions with a proposer that can order them arbitrarily. For each user transaction (e.g., a swap on an AMM), test whether: (a) the attacker can front-run with a same-direction trade, (b) the user transaction executes at a worse price, (c) the attacker back-runs with an opposite-direction trade, and (d) the attacker profits. Account for Stellar's fixed fee model (no priority gas auctions) and 3-5 second ledger close window. Report sandwichable transactions with minimum profit threshold.
- [ ] **Phase 6 — Flash Loan Attack Simulation:** For each protocol that interacts with a lending primitive, test whether an attacker can: (a) take a flash loan of asset X, (b) use the borrowed X to manipulate prices or collateral ratios in a way that allows extracting value Y > X + fees, (c) repay the flash loan, and (d) keep Y - X - fees as profit. The search must explore all possible loan amounts (parameterized as a percentage of pool liquidity) and all possible sequences of operations between borrow and repay.
- [ ] **Phase 7 — Profitability Quantification:** For each found exploit, compute: (a) `required_capital` — the minimum capital needed (may be 0 for flash loans), (b) `gross_profit` — raw profit before fees/gas, (c) `net_profit` — profit after Stellar transaction fees and slippage, (d) `risk_of_revert` — probability of a competing transaction causing revert, (e) `exploit_difficulty` — a 0-1 score based on number of transactions, timing requirements, and capital needs. Only report exploits with `net_profit > 0` and `exploit_difficulty < 0.8` (practically executable).
- [ ] **Phase 8 — Protocol Annotations:** Add a `#[economic_model]` annotation system for Soroban contracts. Developers annotate their contracts with the economic primitives they use: `#[uses_amm(pool_address, token_a, token_b)]`, `#[uses_oracle(oracle_address, price_pair)]`, `#[uses_lending(pool_address, collateral_asset)]`. These annotations feed the framework's model of the protocol without requiring manual configuration.
- [ ] **Phase 9 — Report Generation:** Generate an `EconomicExploitReport` containing: the attack sequence (step-by-step), the economic model used, profit breakdown, required preconditions, and a severity score. Integrate with the `VulnerabilityReport` frontend component to display economic exploits alongside code-level vulnerabilities, distinguished by an `Economic` tag.
- [ ] **Documentation:** Write `docs/ECONOMIC_EXPLOIT_DETECTION.md` covering: the economic primitives library, search algorithm configuration, profitability model, Soroban-specific MEV considerations, limitations (unmodeled off-chain dependencies, market liquidity assumptions), and guidance on interpreting exploit reports.

## Issue 64: [Formal Verification] Implement SMT-Based Formal Verification of Smart Contract Invariants Using Z3

**Priority:** 🔴 Critical
**Area:** Core Scanner / Formal Methods
**Files:** `src/invariants.rs`, `src/security_analyzer.rs`, `src/analysis_guard/ast.rs`

### Description

The invariant engine in `src/invariants.rs` uses regex pattern matching to check 24 invariant rules — it looks for patterns like `checked_add` to verify `OverflowProtection` or `require_auth` to verify `AdminAuthorization`. This approach is fundamentally limited: it can verify that protective code patterns exist, but it cannot prove that the invariant actually holds across all possible executions. A contract can contain `checked_add` on every operation but still overflow if it uses the wrong checked variant or applies it to a derived value rather than the original. A contract can call `require_auth` but on the wrong address or with the wrong arguments.

This issue requires implementing **SMT-based formal verification** that proves invariants are mathematical theorems about the contract's behavior. The approach: (1) translate the contract's WASM bytecode (or a Rust MIR representation) into SMT-LIB2 formulas accepted by the Z3 theorem prover, (2) encode each invariant as a negated assertion (counterexample = invariant violation), (3) use Z3 to either prove the invariant (UNSAT = no counterexample exists) or find a concrete violation (SAT = here's an input that breaks it), and (4) report results with either a "Verified ✓" badge or a concrete counterexample with input values and execution trace.

The technical challenges include: handling loops (must find inductive invariants or bound unrolling), modeling the Soroban host environment (storage, authentication, cross-contract calls) as SMT theories, encoding 128-bit arithmetic precisely (Z3's bit-vector theory supports this), and making the verification practical for real-world contracts (hundreds of functions, thousands of instructions) through modular verification — proving each function's contract independently and composing results.

### Acceptance Criteria

- [ ] **Phase 1 — SMT Encoding of Soroban WASM:** Define a translation from a subset of WASM to SMT-LIB2. Map WASM's i32/i64/i128 values to Z3 `(_ BitVec 32)`, `(_ BitVec 64)`, `(_ BitVec 128)`. Map WASM control flow to SMT `ite` expressions and `assert` blocks. Handle: `i32.add`/`i64.add`/`i128.add` (with overflow flags as separate Boolean outputs), `local.get`/`local.set`, `if`/`else`/`block`/`loop`, `call`/`call_indirect`, `memory.load`/`memory.store` (as array theory select/store). Initially support a subset covering ~80% of Soroban contract instructions; document unsupported instructions.
- [ ] **Phase 2 — Invariant Specification Language:** Design a minimal specification language for invariants embedded in Rust doc comments: `/// #[invariant: forall x: i128, balance_of(x) >= 0]`, `/// #[invariant: total_supply == sum(balance_of(a) for a in all_accounts)]`, `/// #[invariant: old(total_supply) + mint_amount == total_supply]` (for temporal invariants using `old()` for pre-state). Parse these into `InvariantSpec` structs with typed variables, quantifiers, and SMT-LIB2 expressions.
- [ ] **Phase 3 — Host Environment Theory:** Encode Soroban host functions as uninterpreted functions with axioms. `env.storage().get(key)` → uninterpreted function `storage_get: (BitVec 256) -> (BitVec 1024)` with no axioms (any value possible). `require_auth(addr)` → constrains `caller == addr` for the remainder of the path. `env.ledger().timestamp()` → a fresh symbolic variable constrained to be >= the contract's deployment timestamp. Cross-contract `call` → replaces the call with the callee's function summary (pre/post conditions).
- [ ] **Phase 4 — Modular Verification:** Implement function summaries: each function is verified independently. For each function, compute a `FunctionSummary { preconditions: Vec<SmtExpr>, postconditions: Vec<SmtExpr>, modifies: HashSet<StorageKey> }`. The precondition encodes `require_auth` checks and parameter bounds; the postcondition encodes return values and state changes. When a function calls another function, the callee's summary is used instead of its body (modular reasoning). Summaries are computed bottom-up on the call graph.
- [ ] **Phase 5 — Loop Handling:** For simple loops (induction variable, constant bound), unroll fully up to `max_unroll` (default 20). For complex loops, require an inductive invariant annotation: `/// #[invariant: for i in 0..n, processed[i] == true]`. Use Z3's `fp` (fixedpoint) engine to verify inductive invariants when provided. If no invariant is provided and the loop cannot be bounded, report "could not verify — loop requires invariant annotation" rather than a false positive.
- [ ] **Phase 6 — Counterexample Generation:** When Z3 returns SAT, extract the model (concrete values for all symbolic variables). Map these back to a human-readable format: "Invariant `balance_non_negative` violated when `amount = -1`, `from = GABC...`, `to = GDEF...`". Generate a concrete Soroban transaction that would trigger the violation, including function name, arguments, and expected ledger state. This transaction can be submitted to the time-travel debugger for reproduction.
- [ ] **Phase 7 — CI Integration:** Add `stellar-scanner verify --contract <path> --invariants <spec>` as a CI-friendly command. Output a machine-readable JSON report: `{ "contract": "...", "invariants": [ { "name": "...", "status": "verified"|"violated"|"unknown", "counterexample": {...} } ], "time": "12.4s", "solver": "z3 4.12.1" }`. Exit code 0 if all invariants verified, 1 if any violated, 2 if any unknown.
- [ ] **Phase 8 — Benchmark Suite:** Create a suite of 15 contracts: 5 with provably correct invariants (should verify), 5 with known invariant violations (should find counterexamples), and 5 with complex control flow that requires annotations (should report "unknown"). Measure verification time and report which contracts timed out vs. succeeded.
- [ ] **Documentation:** Write `docs/FORMAL_VERIFICATION.md` covering: the invariant specification language syntax, SMT encoding details, supported WASM instruction subset, loop annotation requirements, known limitations, and a guide to writing verifiable invariants.

## Issue 65: [Storage Safety] Detect Storage Key Collisions and Orphaned State Across Contract Upgrades

**Priority:** 🔴 Critical
**Area:** Core Scanner / Storage Safety
**Files:** `src/time_travel_debugger/contract_upgrade.rs`, `src/time_travel_debugger/orphaned_state.rs`, `src/invariants.rs`

### Description

Soroban contracts store persistent data using `env.storage().instance()`, `env.storage().persistent()`, and `env.storage().temporary()`, keyed by `SorobanSymbol` or `SorobanVal`. When a contract is upgraded (new WASM deployed to the same contract ID), the storage from the old contract persists — but the new contract may compute storage keys differently, interpret stored values with different types, or write to overlapping key spaces. This creates two classes of storage bugs:

1. **Storage Key Collisions:** Two different logical pieces of data (e.g., `admin` address and `fee_basis_points`) end up at the same storage key because the key computation changed between versions. The new contract overwrites one with the other, causing data corruption.

2. **Orphaned State:** The old contract stored data at keys that the new contract never reads or writes. This data persists in the ledger forever, bloating state and potentially being exploited if a future upgrade (or downgrade) reads it.

Issue #8 addresses state incompatibility reporting, but it does not perform a **pre-upgrade static analysis** that predicts collisions and orphans before they happen. This issue requires building a static analyzer that: (1) symbolically executes both old and new contract versions to enumerate all possible storage keys they can write, (2) identifies key collisions where two different logical variables map to the same concrete key, (3) identifies orphaned keys that the old contract wrote but the new contract never reads, and (4) identifies type mismatches where the same key holds a different type in the new contract than the old.

### Acceptance Criteria

- [ ] **Phase 1 — Storage Key Extraction:** For each contract WASM, statically extract all `env.storage().{instance,persistent,temporary}().{get,set,has,remove}()` call sites. For each call site, trace the `key` argument back through the dataflow to determine whether the key is: (a) a compile-time constant `Symbol`, (b) computed from function parameters (dynamic), or (c) computed from storage values (data-dependent). Represent each key site as a `StorageAccess { location: SourceLocation, key: KeyExpression, access_type: Get | Set | Has | Remove, storage_type: Instance | Persistent | Temporary }`.
- [ ] **Phase 2 — Key Expression Normalization:** For compile-time constant keys, normalize to a canonical form. For `Symbol::short("admin")`, the internal representation is deterministic. For computed keys (e.g., `Symbol::short("balance_") + user_address`), use a term algebra: `KeyExpr::Concat(Box<KeyExpr>, Box<KeyExpr>)`, `KeyExpr::Symbol(String)`, `KeyExpr::Address(usize)` (referring to a function parameter). Two key expressions are equal iff they are structurally identical after normalization.
- [ ] **Phase 3 — Cross-Version Comparison:** Given old and new WASM, compute the `StorageFootprint` of each: the set of all storage keys the contract can write (for collisions) and the set of all keys it can read (for orphans). A collision exists when: key K is written by both old and new contracts, but the logical source of the value written to K differs between versions. An orphan exists when: key K is written by the old contract but never read or written by the new contract. A type mismatch exists when: the old contract writes a value of type T1 to key K, but the new contract reads key K expecting type T2 (where T1 ≠ T2).
- [ ] **Phase 4 — Type Inference for Stored Values:** For each `set(key, value)` call site, trace the `value` argument to determine its Soroban type: `i32`, `i64`, `i128`, `u32`, `u64`, `u128`, `Symbol`, `Address`, `Bytes`, `Vec`, `Map`, or a custom struct. Use a combination of WASM instruction analysis and Rust ABI conventions (how Rust types map to WASM types in Soroban). Report type mismatches when the old contract writes type T1 but the new contract reads the same key as type T2.
- [ ] **Phase 5 — Dynamic Key Conflict Detection:** For keys computed from function parameters, use a constraint-based analysis: `∀ p1, p2: ParameterValues, key_expr_old(p1) == key_expr_new(p2) ∧ logical_source_old ≠ logical_source_new`. This finds potential collisions that depend on runtime values. Report these as "potential collisions" with the condition under which they occur (e.g., "collision occurs when admin address equals fee recipient address").
- [ ] **Phase 6 — Orphaned State Migration Suggestions:** For each orphaned key, generate a migration suggestion: (a) if the data is obsolete, suggest `env.storage().remove(key)` in the new contract's upgrade migration function, (b) if the data should be migrated to a new key, suggest the old-key-to-new-key mapping, (c) if the data format changed, suggest a type conversion. Generate a skeleton migration function in Rust that the developer can fill in.
- [ ] **Phase 7 — Report Visualization:** Generate a `StorageSafetyReport` containing: a diff table of storage keys (old only, new only, common with same type, common with different type), a collision risk matrix (key → old logical variable → new logical variable → collision condition), and an orphaned key list with size estimates. Integrate with the time-travel debugger's upgrade simulation to validate the report against actual ledger state.
- [ ] **Phase 8 — CI Integration:** Add a `stellar-scanner storage-audit --old <wasm> --new <wasm>` command that runs the analysis and exits with code 1 if any critical collisions or type mismatches are found. This can be used as a pre-upgrade check in CI.
- [ ] **Documentation:** Write `docs/STORAGE_SAFETY_ANALYSIS.md` covering: storage key computation model, collision detection algorithm, type inference approach, interpretation of reports, and best practices for upgrade-safe storage design.

## Issue 66: [Vulnerability Analysis] Cross-Language Vulnerability Propagation Detection Through the Rust → WASM → Soroban VM Compilation Stack

**Priority:** 🟠 High
**Area:** Core Scanner / Multi-Layer Analysis
**Files:** `src/scanners.rs`, `src/analysis_guard/ast.rs`, `src/upload_sanitization/wasm.rs`, `src/differential_fuzzing.rs`

### Description

Soroban contracts are written in Rust, compiled to WASM, and executed on the Soroban VM. Vulnerabilities can be introduced at any layer of this compilation stack, and they can propagate in non-obvious ways:

1. **Rust-level issues** that survive compilation: a `RefCell` panic becomes a WASM trap that rolls back state — which might be exploitable if the panic occurs after partial state changes. A `HashMap` iteration order is non-deterministic and can cause different execution outcomes across validators.

2. **Compiler-introduced issues:** The Rust compiler (rustc) and LLVM apply optimizations that can eliminate security-critical checks. A `checked_add` followed by `unwrap()` might be optimized to `unchecked_add` if LLVM proves the overflow cannot happen — but LLVM's proof might be wrong for edge cases.

3. **WASM-level issues:** WASM's 32-bit address space wraps around at 4GB. A contract that computes offsets near this boundary can create out-of-bounds accesses that appear safe at the Rust level. WASM's `memory.grow` can fail, but many contracts don't check for this.

4. **VM-level issues:** The Soroban VM enforces metering (CPU instructions, memory pages) and can terminate a contract mid-execution. A contract that makes state changes before a metering point can be forced into an inconsistent state.

No existing tool performs **cross-layer vulnerability propagation analysis** — tracing how a vulnerability at one layer manifests at another. This issue requires building an analysis pipeline that: (1) accepts Rust source, WASM binary, and VM configuration, (2) analyzes each layer independently, (3) propagates findings between layers using a formal model of the compilation chain, and (4) reports vulnerabilities that are invisible when analyzing any single layer in isolation.

### Acceptance Criteria

- [ ] **Phase 1 — Multi-Layer IR:** Define a unified `CrossLayerIR` that represents contract behavior at three levels: (a) MIR-level (Rust's Mid-level IR, extracted via `rustc` driver), (b) WASM-level (the `.wasm` binary, parsed and lifted to a control-flow IR), (c) VM-level (the Soroban host function call trace, extracted from the execution tracer in `differential_fuzzing/execution_tracer.rs`). Each instruction in each layer maps to zero or more instructions in adjacent layers via a `CompilationMapping`.
- [ ] **Phase 2 — Compilation Chain Model:** Build a formal mapping from Rust MIR to WASM opcodes for Soroban's specific `wasm32-unknown-unknown` target. Key mappings: MIR `CheckedAdd` → WASM `i128.add` + trap-on-overflow flag, MIR `RefCell::borrow_mut()` → WASM load/store + trap-on-mutex-contention, MIR `panic!()` → WASM `unreachable`, MIR `HashMap::iter()` → WASM non-deterministic iteration order. Document at least 50 mappings covering the most common Rust patterns in Soroban contracts.
- [ ] **Phase 3 — Rust-Level Analysis:** Analyze the Rust source for: (a) interior mutability (`RefCell`, `Cell`, `UnsafeCell`) that can panic, (b) non-deterministic iteration (HashMap, HashSet), (c) platform-specific behavior (`cfg(target_arch = "wasm32")` branches that differ from test), (d) unsafe blocks that make assumptions about WASM memory layout, (e) `catch_unwind` usage that might suppress critical errors. Each finding is tagged with its Rust location and annotated with whether it can propagate to WASM.
- [ ] **Phase 4 — WASM-Level Analysis:** Analyze the compiled WASM for: (a) missing `memory.grow` failure checks, (b) offset computations within 1KB of the 4GB boundary (potential wrap-around), (c) indirect call targets that are not in the export table (potential type confusion), (d) instructions that trap (unreachable, unreachable-branch, out-of-bounds) and their Rust source locations (via DWARF debug info or the compilation mapping). Each finding is annotated with whether the Rust source contained protections that were optimized away.
- [ ] **Phase 5 — Cross-Layer Propagation:** For each finding at one layer, determine if it manifests at another layer. Example: a `RefCell::borrow_mut()` panic at Rust level (no unsafe blocks, so it's "safe Rust") → compiles to a WASM load/store sequence with no trap → at VM level, this is a non-deterministic crash depending on concurrent access patterns. Another example: Rust `checked_add(x, y).unwrap()` → LLVM optimizes to `unchecked_add` because it proves `x + y < 2^128` from the function's precondition → but the precondition is violated by a calling contract → WASM `i128.add` without overflow flag → silent overflow at VM level.
- [ ] **Phase 6 — Optimization Sensitivity Analysis:** Recompile the contract with different optimization levels (`-O0`, `-O1`, `-O2`, `-Os`, `-Oz`) and re-run the WASM analysis for each. Report findings that only appear at certain optimization levels (e.g., a panic is optimized away at `-O2` but present at `-O0`). Flag these as "optimization-sensitive vulnerabilities" with high severity — they can appear or disappear depending on the compiler flags used during deployment.
- [ ] **Phase 7 — VM-Level Fuzzing:** Feed the cross-layer findings to the differential fuzzer: for each finding that involves a potential trap or non-deterministic behavior, generate concrete test inputs that exercise the vulnerable code path and verify the behavior across multiple Soroban SDK versions. Use the `execution_tracer.rs` to record the VM-level execution trace and compare against the predicted behavior from the cross-layer model.
- [ ] **Phase 8 — Report Generation:** Generate a `CrossLayerReport` organized as a three-column table: Rust Finding → WASM Manifestation → VM Impact. Each row is severity-scored based on the worst impact across all layers. Include a "confidence" score based on whether the propagation is certain or speculative. Integrate with the `VulnerabilityReport` frontend.
- [ ] **Documentation:** Write `docs/CROSS_LAYER_ANALYSIS.md` covering: the compilation chain model, the 50+ Rust→WASM mappings, optimization sensitivity methodology, known false positives (spurious LLVM optimizations), and guidance on writing compilation-safe Soroban contracts.

## Issue 67: [Fuzzing] Implement Coverage-Guided Fuzzing with WASM Instrumentation and Feedback-Driven Mutation

**Priority:** 🟠 High
**Area:** Core Scanner / Advanced Fuzzing
**Files:** `src/analysis_guard/fuzz.rs`, `src/differential_fuzzing/input_generator.rs`, `src/differential_fuzzing/test_runner.rs`

### Description

The current fuzzing infrastructure uses deterministic mutations (`src/analysis_guard/fuzz.rs` — bit flip, truncate, duplicate, insert at fixed positions) and a naive test input generator (`src/differential_fuzzing/input_generator.rs` — edge cases like MaxI128, MinI128, but no feedback loop). This is black-box fuzzing: the fuzzer has no visibility into which parts of the contract code were exercised by each input, so it cannot guide mutations toward unexplored code paths. As a result, the fuzzer wastes the majority of its cycles generating inputs that hit the same already-covered code paths.

A **coverage-guided fuzzer** instruments the WASM binary to track which basic blocks, edges (pairs of consecutive blocks), and function calls are executed by each input. The fuzzer maintains a corpus of "interesting" inputs — those that discovered new coverage — and prioritizes mutation of these inputs to discover yet more coverage. This approach, pioneered by AFL and libFuzzer, routinely finds 10-100x more bugs than black-box fuzzing in the same time budget.

The challenge for Soroban: WASM instrumentation must work within the Soroban VM's metering constraints (instrumentation adds instructions, consuming the CPU budget), must not alter the contract's observable behavior (no side effects from instrumentation), and must capture coverage data efficiently (shared memory buffer between the instrumented contract and the fuzzer host). Additionally, the input generator must be able to produce valid Soroban function arguments (Address, Symbol, i128, Vec, Map, structs) — a pure byte-level mutation approach will produce mostly invalid inputs that are rejected during deserialization.

### Acceptance Criteria

- [ ] **Phase 1 — WASM Instrumentation:** Build a WASM instrumentation pass that inserts coverage tracking at each basic block entry. For each block, insert: `global.get $coverage_counter; i32.const BLOCK_ID; i32.const 1; i32.add; global.set $coverage_counter`. The `$coverage_counter` global is exported as `__coverage_counter` and backed by a shared memory page visible to the fuzzer host. Also track edge coverage (block A → block B transitions) by XOR-ing the previous block ID with the current block ID before incrementing a separate edge counter. The instrumentation overhead must be under 20% of the original contract's CPU budget.
- [ ] **Phase 2 — Coverage Map and Corpus:** Implement a `CoverageMap` (bitmap of 65536 entries, one per edge) following AFL's design. After each execution, read the shared memory page and update the global coverage map. An input is "interesting" (added to the corpus) if it triggers any edge not previously seen in the global map. Maintain a `CorpusEntry` for each interesting input containing: the raw input bytes, the execution time, the input size, and the set of new edges discovered.
- [ ] **Phase 3 — Structured Input Generation:** Extend `InputGenerator` to produce valid Soroban function arguments. For each argument type: `Address` → generate a valid Stellar address (G... prefix, 56 chars, valid checksum), `Symbol` → generate ASCII strings within Soroban's 32-char limit, `i128` → generate interesting integers (0, 1, -1, MaxI128, MinI128, powers of 2, and random values with exponential distribution biased toward small values), `Vec` → generate vectors of varying lengths with elements from the appropriate generator, `Map` → generate key-value pairs, `struct` → recursively generate each field. The generator must produce both well-typed inputs (90% of the time) and type-invalid inputs (10%) to test deserialization robustness.
- [ ] **Phase 4 — Mutation Strategies:** Implement a suite of mutation operators: (a) **bit flip** — flip 1/2/4/8/16/32 random bits, (b) **byte flip** — flip, set to 0, set to 0xFF, (c) **arithmetic** — add/subtract small values from integer fields, (d) **interesting values** — replace fields with known edge-case values (0, -1, INT_MAX, INT_MIN), (e) **splice** — take a suffix from another corpus entry and replace the current suffix, (f) **havoc** — apply a random number of random mutations in sequence, (g) **structure-aware splice** — swap entire function arguments between two corpus entries. The mutation scheduler should assign higher selection probability to corpus entries that are smaller and execute faster (AFL's "performance score" heuristic).
- [ ] **Phase 5 — Crash Triage and Deduplication:** When an input causes a crash (panic, trap, or timeout), apply a crash deduplication algorithm: (a) extract the crash stack trace from the Soroban VM host, (b) normalize by removing input-dependent values from the trace, (c) hash the normalized trace, (d) group crashes by hash — only report the first crash in each group as a unique finding. Store the minimal crashing input (use a delta-debugging algorithm to shrink it) alongside the crash report.
- [ ] **Phase 6 — Persistent Mode:** Implement persistent fuzzing mode: instead of spawning a new VM instance for each input (typical fork+exec overhead), keep a single long-lived VM instance and reset its state between inputs. The reset must clear: storage, memory (re-initialize from the original WASM data segments), globals, and the call stack. This reduces per-input overhead from ~50ms to ~1ms, allowing 1000+ executions per second instead of 20.
- [ ] **Phase 7 — Fuzzing Dashboard:** Add a `GET /api/v1/fuzzer/status` endpoint and a frontend `FuzzerDashboard` component displaying: total executions, executions/second, corpus size, coverage map visualization (heatmap of covered edges), unique crashes found, time since last new coverage, and estimated time to completion. The dashboard should update in real-time via WebSocket.
- [ ] **Phase 8 — CI Integration:** Add a `stellar-scanner fuzz --timeout 3600 --corpus-dir <path>` command for CI. The fuzzer runs for the specified timeout, saves the corpus to the specified directory (for caching between CI runs), and exits with code 1 if any crashes are found. The corpus directory should be cached in GitHub Actions to enable incremental fuzzing across CI runs.
- [ ] **Phase 9 — Differential Fuzzing Integration:** Integrate coverage guidance with the differential fuzzer: inputs that produce different behavior across SDK versions are treated as "interesting" even if they don't increase coverage. This combines the strengths of both approaches: coverage guidance for thorough exploration, differential comparison for discrepancy detection.
- [ ] **Documentation:** Write `docs/COVERAGE_GUIDED_FUZZING.md` covering: WASM instrumentation design, coverage map encoding, mutation strategy details, persistent mode architecture, corpus management, and CI configuration examples.

## Issue 68: [Protocol Analysis] Protocol-Level Invariant Verification Across Multi-Contract Systems

**Priority:** 🟠 High
**Area:** Core Scanner / Protocol Security
**Files:** `src/invariants.rs`, `src/differential_fuzzing/cross_contract_simulator.rs`, `src/scanners.rs`

### Description

The invariant engine checks invariants on individual contracts — e.g., "this token contract's total supply equals sum of balances." But real Soroban protocols involve 5–20 contracts working together: token contracts, pool contracts, factory contracts, fee distributors, governance contracts, and oracles. Protocol-level invariants span multiple contracts and are far more economically meaningful:

- *DEX Invariant:* The product of reserves in Pool A plus Pool B (for a token pair) must remain constant before and after any non-swap operation.
- *Lending Protocol Invariant:* The total deposits across all lending pools must equal total loans outstanding plus available liquidity, minus protocol fees.
- *Stablecoin Invariant:* The total supply of the stablecoin must equal the total collateral value (in USD terms) across all vaults, divided by the collateralization ratio.
- *Bridge Invariant:* The total tokens locked on Soroban must equal the total tokens minted on the counterpart chain (and vice versa), accounting for in-flight transfers.

These invariants cannot be verified by checking any single contract in isolation — they require reasoning about the protocol as a system. This issue requires building a **protocol-level invariant verification system** that: (1) ingests a protocol specification (set of contract addresses + their WASM code + a description of how they interact), (2) extracts protocol-level invariants from developer annotations or auto-infers them from the protocol's economic design, (3) verifies them using a combination of static analysis (for structural properties) and dynamic simulation (for economic properties), and (4) reports violations with cross-contract call sequences that trigger them.

### Acceptance Criteria

- [ ] **Phase 1 — Protocol Specification Format:** Design a `ProtocolManifest` YAML/JSON format that describes a multi-contract protocol: `contracts: [{name, address, wasm_path, role}]`, `interactions: [{from_contract, from_function, to_contract, to_function}]`, `invariants: [{name, description, expression}]`. The `expression` field uses a simple DSL: `sum(balances[pool_a][token_x], balances[pool_b][token_x]) == total_supply[token_x]`. Support arithmetic, summation over collections, comparison, and temporal operators (`before`/`after`).
- [ ] **Phase 2 — Protocol Invariant Auto-Inference:** For common protocol patterns, auto-infer invariants: (a) for any AMM pool, infer `reserve_x * reserve_y == k` (constant product), (b) for any lending pool, infer `total_deposits >= total_loans`, (c) for any wrapped/bridged token, infer `locked_on_chain_a == minted_on_chain_b`, (d) for any governance token, infer `total_voting_power == sum(delegated_power)`. The auto-inference uses pattern matching on the contract's function signatures and storage layout.
- [ ] **Phase 3 — Static Protocol Analysis:** For structural invariants (those that can be proven from the code alone), apply a modular verification approach: (a) prove each individual contract function satisfies its specified pre/post-conditions, (b) compose the results across the call graph to prove protocol-level properties. Use the SMT-based verifier from Issue #64 for individual contracts. For protocols that don't fit the SMT model, fall back to bounded model checking: unroll the cross-contract call graph to depth K and exhaustively test all paths using concrete execution.
- [ ] **Phase 4 — Dynamic Protocol Simulation:** For economic invariants (those that depend on market dynamics), build a protocol simulator that: (a) initializes all contracts with the protocol's genesis state, (b) generates random sequences of user operations (swaps, deposits, borrows, repays, liquidations) drawn from realistic distributions, (c) after each operation, checks all protocol invariants, (d) if an invariant is violated, records the operation sequence that triggered it. Run the simulator for `N` steps (default 100,000) and report any invariant violations found within that horizon.
- [ ] **Phase 5 — Cross-Contract Call Graph Analysis:** Build a `ProtocolCallGraph` that captures not just which contracts call which (as in Issue #62) but the *protocol-level control flow*: entry point → authentication → validation → core logic → state updates → event emission → cross-contract calls → cleanup. Annotate the graph with the protocol invariants that must hold at each node. Use this to identify "invariant-critical sections" — sequences of operations where a protocol invariant is temporarily broken and must be restored before the sequence ends.
- [ ] **Phase 6 — Adversarial Protocol Exploration:** Extend the economic exploit framework from Issue #63 to target protocol-level invariants. An attacker agent attempts to find sequences of operations across multiple contracts that violate a protocol-level invariant and produce profit. The agent can interact with any contract in the protocol, not just a single vulnerable contract. Report protocol-level exploits separately from single-contract exploits.
- [ ] **Phase 7 — Protocol Health Dashboard:** Create a `ProtocolHealth` dashboard that shows, for a registered protocol: all defined invariants with their current verification status (✓ verified / ⚠ unknown / ✗ violated), a protocol call graph visualization with invariant annotations, a simulation coverage heatmap (which parts of the protocol have been exercised by the simulator), and a list of recent invariant violations with reproduction steps.
- [ ] **Phase 8 — CI Integration:** Add `stellar-scanner protocol-verify --manifest protocol.yaml [--simulation-steps N]` that: (a) loads the protocol manifest, (b) runs static verification on all structural invariants, (c) runs dynamic simulation on all economic invariants, (d) outputs a combined report, and (e) exits with code 0 if all invariants hold, 1 if any are violated, 2 if any are unprovable.
- [ ] **Documentation:** Write `docs/PROTOCOL_LEVEL_VERIFICATION.md` covering: the protocol manifest format, invariant specification DSL, auto-inference rules for common protocol patterns, static vs. dynamic verification strategy selection, simulation configuration, and interpretation of protocol health reports.
